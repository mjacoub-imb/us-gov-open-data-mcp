# Microsoft Entra ID (Azure AD) sign-in

By default the HTTP transport authenticates with one shared secret
(`MCP_AUTH_TOKEN`). That works, but it doesn't scale to a team: there's no
per-person identity, no way to cut off one leaver, and rotating it forces
everyone to reconfigure at once.

Enabling Entra ID lets teammates click **Individual sign-in** with their normal
Microsoft work account. No extra npm package is needed — the OAuth provider
ships with `fastmcp`.

Both credential types work at the same time, so enabling this does **not**
break existing token-based clients (Claude Code CLI, scripts, CI).

## 1. Create the App Registration

In the [Azure portal](https://portal.azure.com) → **Microsoft Entra ID** →
**App registrations** → **New registration**:

| Field | Value |
| --- | --- |
| **Name** | Anything — this is shown on the sign-in prompt (e.g. "Gov Data MCP") |
| **Supported account types** | **Accounts in this organizational directory only** |
| **Redirect URI** | Platform **Web**, value `<MCP_PUBLIC_URL>/oauth/callback` |

Two things worth getting right the first time:

- Choose the **Web** platform, not **SPA**. SPA registrations refuse to accept a
  client secret, and you need one here.
- **Supported account types** is the real access boundary. "Accounts in this
  organizational directory only" is what confines sign-in to your company;
  `AZURE_TENANT_ID` is a second layer, not a substitute.

Then **Certificates & secrets** → **New client secret**. Copy the *Value*
immediately — it's only shown once. **Note its expiry date**: Entra caps
secrets at 24 months, and logins stop working when it lapses with no other
warning.

Finally, from **Overview**, copy the **Application (client) ID** and the
**Directory (tenant) ID**.

::: tip Restricting further than "everyone in the tenant"
A single-tenant app admits **everyone in your directory — including B2B guest
users** invited to a Teams channel or a SharePoint share. That's often a much
wider group than employees.

To limit it to specific people or groups: **Enterprise applications** → your app
→ **Properties** → set **Assignment required?** to **Yes**, then assign users
or groups under **Users and groups**. This is enforced by Entra, not by this
server.
:::

## 2. Set the environment variables

On Railway (or whichever host), add:

| Variable | Value |
| --- | --- |
| `AZURE_CLIENT_ID` | Application (client) ID |
| `AZURE_CLIENT_SECRET` | The secret *Value* you copied |
| `AZURE_TENANT_ID` | Directory (tenant) ID |
| `MCP_PUBLIC_URL` | Your exact public origin, e.g. `https://your-app.up.railway.app` |

`MCP_PUBLIC_URL` must be a bare origin — **no trailing slash, no path**. Entra
matches redirect URIs by exact string, so a stray slash produces
`https://host//oauth/callback` and fails at first login with `AADSTS50011`. The
server checks this at startup and refuses to boot rather than letting you find
out later.

On the next deploy the startup log prints the value to register:

```
Auth: static token + Microsoft OAuth
Entra redirect URI (must match App Registration exactly): https://your-app.up.railway.app/oauth/callback
```

## 3. Connect from Claude

**Claude Desktop / claude.ai** — Settings → Connectors → **Add custom
connector**, enter `https://your-app.up.railway.app/mcp`, then **Connect** and
complete the Microsoft prompt. On Team/Enterprise plans an owner can add it once
under Admin settings → Connectors and members just click Connect.

**Claude Code** — the shared token remains the simplest option:

```bash
claude mcp add --transport http gov-data https://your-app.up.railway.app/mcp \
  --header "Authorization: Bearer $MCP_AUTH_TOKEN"
```

You'll see a plain, unbranded consent page served from your own domain before
the Microsoft prompt. That's expected — it's generated by the OAuth proxy, not
a phishing page.

## Security notes

**The redirect allowlist is enforced by this server, not by the library.**
`fastmcp`'s own redirect check falls open (it accepts any `https:` URI when no
pattern matches), and its `/oauth/authorize` never validated `redirect_uri` at
all. This server therefore replaces two of the library's OAuth routes with
hardened versions (`src/server/oauth-routes.ts`) that:

- strip the upstream client secret from Dynamic Client Registration responses —
  the stock implementation returns your Entra app's `client_secret` to any
  anonymous caller;
- enforce an exact redirect allowlist on `/oauth/authorize`, so an
  authorization code can't be delivered to an attacker-controlled host;
- require PKCE with `S256`, which the stock implementation treats as optional.

Both are covered by regression tests in `tests/oauth-guards.test.ts`.

**Sessions do not survive a restart.** OAuth session storage is in-memory, so
every redeploy signs everyone out and they re-run the (fast) sign-in. Setting
`MCP_OAUTH_JWT_SIGNING_KEY`/`MCP_OAUTH_ENCRYPTION_KEY` does *not* change this —
persisting sessions would require an external store.

**Run a single replica.** The OAuth login handshake keeps state in-process, and
there are no sticky sessions, so a second replica breaks logins mid-flow with
"Invalid or expired state".

**Identity is attribution, not authorization.** Anyone who signs in can use all
tools and therefore all configured upstream API keys. Entra tells you *who* did
something; it doesn't reduce what they can do.

## Turning the shared token off

Once everyone is on Microsoft sign-in, either delete `MCP_AUTH_TOKEN`, or set
`MCP_AUTH_MODE=oauth` to have it ignored while leaving the value in place. The
latter is the faster response if the token ever leaks.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Server exits at boot listing `✗` errors | Read them — each names the exact variable. All problems are reported at once. |
| `AADSTS50011` (redirect mismatch) | The App Registration URI doesn't exactly equal `<MCP_PUBLIC_URL>/oauth/callback`. Compare against the startup log line. |
| `AADSTS700016` (app not found in directory) | `AZURE_TENANT_ID` and the App Registration are in different tenants. |
| Login worked, then everyone signed out | Expected after a redeploy — see "Sessions do not survive a restart". |
| Logins suddenly fail months later | The client secret expired. Create a new one and update `AZURE_CLIENT_SECRET`. |
| `invalid_request: redirect_uri is not on this server's allowlist` | A client is using a callback URL that isn't allowed. Add it to `MCP_OAUTH_REDIRECT_PATTERNS`. |
